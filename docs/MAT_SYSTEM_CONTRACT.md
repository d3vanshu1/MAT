# MAT System Contract

## Purpose

The Memo Audit Tool (MAT) reviews private-equity Investment Committee memos against supporting deal materials. It is intended to identify:

- numeric discrepancies between IC memos and financial models;
- material risks disclosed in diligence reports;
- material omissions from IC memos;
- cross-version changes between memo or model versions; and
- unsupported, duplicated, or fabricated findings generated by MAT itself.

MAT operates under a hard serverless execution limit and must checkpoint and resume without changing, dropping, duplicating, or silently approving findings.

This file defines stable system-level rules. It is not a task list. Changes to this file should be rare and deliberate.

## Core principle

A successful API call, completed TypeScript build, populated database row, or polished report does not prove MAT is correct.

A MAT result is acceptable only when the relevant process invariant is demonstrated through the actual production data path.

## Canonical process stages

MAT should be understood as a staged process:

1. Input registration and source classification
2. Document and spreadsheet extraction
3. Claim and candidate-finding generation
4. Numeric and qualitative validation
5. Finding identity and family assignment
6. Merge, reduction, and disposition
7. Materiality and severity assessment
8. Omission or absence verification
9. Final canonical persistence
10. Output API, UI, and export
11. Timeout, resume, and recovery paths

Each stage must have explicit inputs, outputs, terminal states, and failure semantics.

## Canonical finding artifact

A final finding must have one canonical representation. Main execution, background execution, timeout/resume, recovery, output APIs, UI, and export must read or derive from the same canonical artifact.

A canonical finding should retain, where applicable:

- `finding_id`
- `finding_kind`
- `issue_key`
- category
- severity
- severity anchor and rationale
- claim IDs
- source documents
- evidence
- evidence coordinates
- metric
- period
- scope
- unit
- entity
- actual/forecast status
- accounting basis
- structured impact
- verification status
- omission or gap metadata
- materiality rationale
- `numeric_unverified`
- `merged_from_finding_ids`
- reduction and disposition history

A field is not considered implemented merely because it exists in a schema. It must be populated meaningfully, preserved, validated, read by its consumer, and used to control the downstream decision.

## Run completeness contract

A run must not be marked publishable or complete unless:

- all required inputs are registered;
- all expected work units are known;
- every required work unit reaches a valid terminal state;
- all merge nodes implied by the run manifest are resolved;
- no required cursor remains unresolved;
- no branch is silently dropped;
- no checkpoint is stale relative to the final artifact;
- degraded fallbacks are recorded explicitly;
- the final artifact is tied to the completed run; and
- publication eligibility is evaluated from persisted production state, not from a local assumption.

Partial, missing, failed, timed-out, unparsable, or unresolved work must not be translated into a substantive conclusion such as “no issue,” “not omitted,” “verified,” or “complete.”

## Evidence and provenance contract

Every final finding must be reconstructable by a reviewer without trusting generated prose.

The evidence chain should identify:

- the memo claim or omission being assessed;
- the supporting or contradicting source;
- exact page, sheet, cell, table, or other coordinate where available;
- the relevant quotation or extracted value;
- the comparison dimensions;
- the validation decision;
- merge ancestry;
- reduction disposition; and
- severity reasoning.

Evidence, provenance, and ancestry must survive serialization, checkpointing, reload, merge, consolidation, materiality, omission verification, persistence, API output, and export.

## Numeric comparison contract

Language models may propose candidate figures or candidate relationships. They must not make the final comparability or arithmetic decision.

A numeric finding must not be retained unless the process establishes, where relevant:

- metric identity;
- period;
- entity;
- scope;
- unit;
- currency;
- actual versus forecast status;
- accounting basis;
- reported versus pro forma status;
- group versus segment status; and
- exact source coordinate.

Comparisons must fail closed when dimensions are incompatible or unknown.

The final delta must be calculated by code from extracted values. Generated arithmetic is not authoritative.

## Source-authority contract

Source authority must be explicit and enforced.

Typical rules include:

- live financial model for numeric ground truth;
- legal due diligence for legal, IP, lease, regulatory, and contractual matters;
- financial due diligence for financial diligence matters;
- commercial due diligence for commercial matters;
- IC memos for the claims and disclosures being assessed;
- management materials as supporting, not automatically authoritative, evidence; and
- external research only where the workflow explicitly permits it.

A lower-authority source must not silently override an authoritative source. Conflicts should be preserved as conflicts unless a deterministic policy resolves them.

## Finding identity and deduplication contract

Findings should be typed and identified before semantic reduction.

Identity should use structured dimensions such as:

- finding kind;
- issue family;
- affected entity;
- affected contract, property, product, obligation, or metric;
- period;
- source authority;
- legal provision or issue type; and
- evidence coordinates.

Every candidate must be persisted exactly once. Diagnostics and invalid entries must remain diagnostics and must not be concatenated back into final findings.

Every removed or merged finding must have a recorded disposition such as:

- exact duplicate;
- same family, merged;
- unsupported;
- wrong source;
- incompatible numeric comparison;
- stale;
- immaterial;
- already disclosed;
- process diagnostic;
- retained; or
- unresolved and publication-blocking.

No finding may disappear without a recorded reason.

## Severity and materiality contract

Severity must be based on structured evidence and explicit anchors, not rhetorical intensity.

A severity decision should account for:

- financial magnitude;
- legal or regulatory consequence;
- transaction impact;
- operational impact;
- source authority;
- certainty;
- reversibility; and
- whether the issue is already disclosed.

Unknown magnitude or uncertainty must not be converted automatically into critical severity.

## Omission contract

An omission finding requires evidence that:

1. the source issue is supported;
2. the relevant memo was searched with adequate coverage;
3. the issue is material enough to require disclosure under the applicable rules; and
4. the issue is not already disclosed in substance.

Incomplete memo processing, missing claims extraction, query failure, or unavailable evidence must block the omission conclusion rather than support it.

## Execution-path equivalence contract

For the same frozen inputs and configuration, the following paths must produce the same canonical finding artifact or fail visibly:

- uninterrupted main execution;
- background execution;
- timeout and resume;
- manual or automated recovery;
- final persistence;
- output API;
- UI rendering; and
- export.

Equivalence should be assessed using canonical IDs, structured content, ancestry, dispositions, artifact status, and hashes where available. Formatting differences alone are not substantive.

## Failure semantics

Infrastructure and process failures must remain process failures.

Examples include:

- database query error;
- missing row;
- wrong schema or column;
- timeout;
- payload truncation;
- parse failure;
- empty artifact;
- disabled integration test;
- missing source coordinate;
- missing model sheet;
- incomplete manifest; or
- unresolved merge node.

These conditions must not become substantive approvals, rejections, or findings.

## Publication contract

The final report must be rendered only from an explicitly complete, canonical, persisted artifact.

The UI and export must not read stale, intermediate, degraded, or differently shaped artifacts.

A report may be generated only when publication eligibility is demonstrated from persisted production state.

## Review standard

Use narrow implementation claims.

Examples:

- “Schema exists” is not “schema is enforced.”
- “Field is written” is not “field survives and controls the consumer.”
- “API returned success” is not “production behavior is correct.”
- “Test passes” is not “all applicable paths are verified.”
- “Run completed” is not “all expected work completed.”

## Scope discipline

Only one active invariant should be implemented at a time unless the active task explicitly defines a tightly coupled vertical slice.

Do not make opportunistic cleanups, broad refactors, unrelated schema changes, prompt rewrites, or nearby fixes in the same task.

## Current product position

Until all relevant contracts above are demonstrated, MAT must be treated as an analyst-assistance system requiring human review. It must not be described as producing independently auditable IC diligence reports.
